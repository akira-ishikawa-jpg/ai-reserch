# GAP ANALYSIS: 四季廻りの職人 vs オクトパストラベラー HD-2D

**作成日:** 2026-03-23
**対象:** 四季廻りの職人（現行ビルド） vs Octopath Traveler（HD-2D町マップ）
**目的:** ビジュアル品質の差分を正直に評価し、実現可能なアクションを特定する

---

## 1. ギャップの正直な評価（スコア）

OTの町マップを10点満点とした場合の、現行「四季廻りの職人」の達成度。

| 要素 | OT基準 (10) | 現行スコア | ギャップ | 備考 |
|------|:-----------:|:---------:|:-------:|------|
| **建築物の複雑さ** | 10 | **1.0** | 9.0 | 壁タイルの塊であり「建物」が存在しない。OTは1棟あたり10以上のパーツ・3面描画 |
| **建築物の多様性** | 10 | **0.5** | 9.5 | 全壁タイルが同一テクスチャ。OTは全建物のデザインが異なる |
| **地面の精密さ** | 10 | **2.0** | 8.0 | 石畳パターンはあるが単一タイルの繰り返し。OTは放射状パターン・段差・高低差あり |
| **装飾オブジェクト** | 10 | **1.5** | 8.5 | 宝箱・セーブポイント・柵のみ。OTは噴水・花壇・街灯・樽・旗・石像など20種以上 |
| **植生** | 10 | **2.0** | 8.0 | 桜の木1種・草タイル1種。OTは大木・蔦・花・草が複数種類で建物に絡む |
| **キャラクター** | 10 | **1.5** | 8.5 | 8x9ピクセルパターンをscale=3で拡大。OTは16x24以上の高品質手描きスプライト |
| **ライティング** | 10 | **4.0** | 6.0 | ポイントライト・ゴッドレイ・グローバルライト方向は実装済み。ただしOTの「面ごとの陰影」「光源からの反射」には未到達 |
| **大気・ポストプロセス** | 10 | **5.5** | 4.5 | ビネット・被写界深度・季節ティント・カラーグレーディング実装済み。PixiJS活用。ここは相対的に近い |
| **パーティクル** | 10 | **5.0** | 5.0 | 桜吹雪・蛍・紅葉・雪・ダストが実装済み。季節ごとの挙動も分化。OTは量と緻密さで上回る |
| **奥行き・パース** | 10 | **2.5** | 7.5 | Y軸75%圧縮のクォータービューは実装済みだが、オブジェクトの重なり・前後関係・3D的な厚みが不足 |
| **全体的な印象** | 10 | **2.0** | 8.0 | ポストプロセスで「雰囲気」は出ているが、「中身」のアセット品質が圧倒的に不足 |

### 総合スコア: **2.5 / 10**

**率直な結論:** ポストプロセスとエフェクト層は4〜5割程度の到達度があるが、ゲームの見た目の大部分を占める**アセット（建物・地面・キャラクター・装飾物）**が根本的に不足しており、全体としてはOTの1/4程度。

## 2. 根本的な限界の分析

### 2.1 現在のスタックの上限

**技術スタック:** HTML5 Canvas 2D + PixiJS（エフェクトオーバーレイのみ）+ コード生成グラフィック

この構成で**理論上到達可能な上限**は以下の通り:

| 要素 | 理論上限 | 理由 |
|------|---------|------|
| ポストプロセス | 7〜8/10 | PixiJS WebGLフィルタで大半のエフェクトは再現可能 |
| パーティクル | 7/10 | Canvas 2D + WebGLの組み合わせで十分な量と品質を出せる |
| ライティング | 5〜6/10 | 動的ライトマップは可能だが、面ごとの法線ベースライティングはCanvas 2Dでは困難 |
| タイルマップ品質 | **3/10が上限** | コード生成（`fillRect` + `noiseRect`）では手描きピクセルアートの質感に到達不可能 |
| 建物 | **2/10が上限** | タイルの組み合わせで「建物風の形」は作れるが、個別デザインの建築物は不可能 |
| キャラクター | **2/10が上限** | 8x9のASCIIパターンでは表現の限界。16色パレット+手動ピクセル配置では動きも表情も不足 |
| 装飾オブジェクト | **2/10が上限** | 個別にコードで描くことは可能だが、1つあたりの工数が膨大で種類を増やせない |

### 2.2 OTレベルに到達するために絶対に必要なもの

**OTのHD-2Dビジュアルの本質は3つ:**

1. **手描きの高品質ピクセルアートアセット**
   - OTの1つの建物は数百〜数千ピクセルの手描きアートで構成されている
   - これはコード生成（`fillRect`の組み合わせ）では**根本的に不可能**
   - `noiseRect` や `dither` 関数で生成できるのは「テクスチャ的なノイズ」であり、「デザインされた構造物」ではない

2. **レイヤー構造のマップシステム**
   - OTのマップは単一の2Dグリッドではなく、地面レイヤー・建物レイヤー・装飾レイヤー・前景レイヤーが分離
   - 前景のオブジェクト（柵・木）がキャラクターの前に描画され、奥のオブジェクトが後ろに描画される
   - 現行は「タイル番号の2Dグリッド1枚」のみ

3. **多様なオブジェクトの大量配置**
   - OTの町は10棟以上の異なる建物 + 20種以上の装飾 + 複数の植生 + 複数のNPC
   - 現行はタイル4種（床・壁・水・入口）+ オブジェクト3種（宝箱・セーブ・NPC）

### 2.3 「改善」vs「作り直し」の判定

| 要素 | 判定 | 理由 |
|------|------|------|
| ポストプロセスエフェクト | **改善で対応可能** | 既存のPixiRenderer基盤を拡張するだけ |
| パーティクルシステム | **改善で対応可能** | 量と種類を増やすチューニング |
| ライティングシステム | **改善で対応可能** | タイルマップベースの事前計算ライトマップを追加 |
| タイルアセット | **作り直し必須** | コード生成から画像アセットへの移行が必要 |
| 建物システム | **作り直し必須** | グリッドタイルから「構造物オブジェクト」への設計変更が必要 |
| キャラクタースプライト | **作り直し必須** | 8x9パターンから最低16x24の画像スプライトへ |
| マップ構造 | **作り直し必須** | 単一グリッドからマルチレイヤーマップへ |
| 装飾オブジェクト | **作り直し必須** | コード描画から画像アセット+配置システムへ |

**結論: ゲームの見た目の80%を占める要素が「作り直し必須」。**

## 3. 実現可能性の3段階評価

### Tier A: 現在のCanvas 2D + コード生成で到達可能な最高品質

**到達見込み: 3.5〜4.0 / 10**

やれること:
- タイルバリエーションの増加（同じコード生成方式で床3種・壁5種など）
- 壁タイルに「上面+正面+側面」の3面描画を追加（現行2面 → 3面）
- 装飾タイルの追加（コード生成で花壇・街灯・樽などを20種類追加）
- マルチレイヤー描画の実装（地面→建物→キャラ→前景の描画順制御）
- ライトマップの事前計算
- ポストプロセスの更なる強化

限界:
- 全てがプログラマティックな「矩形の組み合わせ」から抜け出せない
- 曲線・有機的な形状・グラデーションの手描き感が出ない
- 1つの装飾を追加するたびに100行以上のコードが必要で、スケールしない
- **「ゲームの見た目がドット絵に見えない」問題が解消されない**

工数目安: 2〜3週間

---

### Tier B: アセット画像（手描きまたはAI生成）を導入した場合

**到達見込み: 5.5〜7.0 / 10**

変わること:
- **タイルセット → 画像ファイル（PNG）に移行**
  - AI画像生成ツール（Stable Diffusion, Midjourney等）でHD-2D風タイルを生成
  - または手描きピクセルアートを外注/自作
  - Aseprite等のツールでスプライトシートを作成
- **建物 → 大型スプライト（64x96, 96x128等）として個別画像に**
  - 1棟ごとに異なるデザインの画像を配置
  - 3面描画（屋根・正面・側面）が画像内で完結
- **キャラクター → 16x24以上のスプライトシート**
  - 4方向 x 3フレーム = 12パターン以上
  - 表情・装備の差分も可能
- **装飾オブジェクト → 画像として大量追加が容易**
  - 噴水・花壇・街灯・樽・旗・石像等を画像で配置
- **マップエディタ（Tiled等）の導入**
  - レイヤー管理・衝突判定・オブジェクト配置がGUIで可能

技術的な変更点:
- `generate_tiles.js` の出力を使い続けるが、手描き/AI生成画像に置き換え
- `sprite_loader.js` を拡張して大型スプライトに対応
- `exploration.js` のマップ描画をマルチレイヤー対応に
- Canvas 2D描画はそのまま使える（`drawImage`でアセットを描画）
- PixiRendererも既存のまま活用可能

残る限界:
- Canvas 2Dの描画パフォーマンス（大量オブジェクトで60FPS維持が困難になる可能性）
- シェーダーベースの高度なライティング（法線マップ等）は不可
- OTの「ゴッドレイが建物の間を通り抜ける」ような動的光源処理は困難

工数目安: 1〜2ヶ月（アセット制作含む）

---

### Tier C: ゲームエンジン（Godot/Unity）に移行した場合

**到達見込み: 8.0〜9.5 / 10（アセット品質次第で上限なし）**

変わること:
- **シェーダーベースのライティング**
  - 法線マップ（Normal Map）によるピクセルアートへの動的ライティング
  - ゴッドレイ・ボリュメトリックフォグがネイティブ対応
  - スクリーンスペースのブルーム・カラーグレーディングがGPUで高速処理
- **タイルマップエディタ内蔵**（Godotの場合）
  - レイヤー管理・オートタイル・衝突判定が標準機能
- **パーティクルシステムのGPU処理**
  - 数千パーティクルでも60FPS維持
- **被写界深度のリアルタイム処理**
  - Zバッファベースの正確なDOF
- **マルチプラットフォーム出力**
  - Web / Desktop / Mobile にワンクリックビルド

Godotの場合の具体的な構成:
- Godot 4.x + GDScript
- TileMapLayer（マルチレイヤー）
- CanvasItem Shader で法線マップライティング
- GPUParticles2D で季節エフェクト
- WorldEnvironment でポストプロセス
- 既存のゲームロジック（JS）はGDScriptに書き直し

失うもの:
- **ブラウザでURLアクセスだけで動く手軽さ**（Godot WebエクスポートでHTML5版は可能だが、バイナリサイズが大きい）
- 既存コードの全面書き直しが必要
- ゲームエンジンの学習コスト

工数目安: 2〜4ヶ月（エンジン学習+全面書き直し+アセット制作）

## 4. 推奨アクション

### 判断基準

| 選択肢 | 条件 | ROI |
|--------|------|-----|
| **A: 今のまま改善を続ける** | HD-2Dビジュアルが最優先ではなく、ゲームプレイ・ストーリーの検証が目的の場合 | 高（少ない工数でゲーム全体の完成度を上げられる） |
| **B: アセット画像を導入する** | HD-2Dの「雰囲気」を出したいが、OT完全再現は求めない場合。**最も推奨** | 中〜高（見た目が劇的に改善される。エンジン移行なしで大幅向上） |
| **C: ゲームエンジンに移行** | OTレベルのビジュアル品質が必須要件の場合。長期プロジェクトとして本気で作る場合 | 低〜中（初期投資が大きいが、上限が高い） |

### コストとリターン分析

```
リターン（ビジュアル改善度）
  ^
  |                                    C ●
  |                               ・・・
  |                          ・・
  |                     ・・
  |              B ●・・
  |           ・・
  |        ・・
  |     ・
  |  A ●
  |・
  +---------------------------------> コスト（工数）
  0   2w    1m      2m      3m    4m
```

**推奨: Tier B（アセット画像の導入）**

理由:
1. 既存のCanvas 2D + PixiJSアーキテクチャをそのまま活用できる
2. コード変更は主に「描画部分の`fillRect`を`drawImage`に置き換える」のみ
3. AI画像生成を使えばアセット制作コストを大幅に削減可能
4. ビジュアル品質が2.5 → 5.5〜7.0に跳ね上がる（コスパ最大）
5. 将来的にゲームエンジンに移行する場合も、アセット画像はそのまま使い回せる

## 5. 現在のスタックで最大限頑張る場合のアクションリスト

**パレートの法則: 20%の工数で80%の改善を得るための優先順位**

### 第1優先（効果: 大、工数: 小〜中）— 1週間

#### 1-1. 壁タイルのバリエーション追加と建物らしい形の構築
- 壁タイルに「窓あり壁」「扉壁」「屋根タイル」「看板タイル」を追加（各40〜60行のコード）
- これらを組み合わせて「建物に見える配置パターン」をマップデータに反映
- **効果:** 「壁の塊」→「建物っぽい形」に見え方が変わる
- **スコア変化:** 建築物 1.0 → 2.5

#### 1-2. 床タイルのバリエーション追加
- 石畳（大）・石畳（小）・レンガ・土道・木の床・花びら散る石畳の6種を追加
- マップ上でエリアごとに使い分ける
- **効果:** 「同じ床の繰り返し」→「場所ごとに異なる地面」
- **スコア変化:** 地面 2.0 → 3.5

#### 1-3. マルチレイヤー描画の実装
- `exploration.js` の描画順を「地面 → 壁下部 → キャラ → 壁上部・木」に変更
- Y座標ソートによる前後関係の正しい描画
- **効果:** キャラが建物の裏に隠れる、木の前を歩ける → 奥行き感が大幅向上
- **スコア変化:** 奥行き 2.5 → 4.5

### 第2優先（効果: 中、工数: 中）— 1〜2週間

#### 2-1. 装飾オブジェクトの大量追加
- コード生成で以下を追加: 噴水・花壇・街灯・樽・木箱・井戸・ベンチ・旗竿
- 各オブジェクトを32x32または32x64のタイルとして描画関数を追加
- マップデータに装飾レイヤーを追加
- **効果:** 町がにぎやかになる
- **スコア変化:** 装飾 1.5 → 3.5

#### 2-2. タイルベースのライトマップ
- マップ読み込み時に各タイルの「明るさ」を事前計算
- 壁際の影・光源からの距離に基づく明暗を適用
- **効果:** 平坦だった明るさにメリハリが出る
- **スコア変化:** ライティング 4.0 → 5.5

#### 2-3. キャラクターサイズの拡大
- 8x9パターンを12x16に拡大（パレット色数も増加）
- 4方向 x 3フレームのアニメーション
- **効果:** キャラクターの「ドット感」が向上
- **スコア変化:** キャラクター 1.5 → 2.5

### 第3優先（効果: 小〜中、工数: 中〜大）— オプション

#### 3-1. 大型構造物スプライト
- 特定の建物を「タイルの組み合わせ」ではなく1つの大きなコード生成スプライトとして描画
- 例: 薬師ギルドを64x96のカスタム描画関数で1つの建物として描く
- **効果:** 「建物」としての説得力が増す
- **工数:** 1建物あたり200〜400行。5棟で1000〜2000行

#### 3-2. 水面の反射エフェクト
- 水タイルに隣接する建物・キャラの反転描画
- **効果:** OTの印象的なビジュアル要素の1つを再現

#### 3-3. 季節ごとのタイルセット切り替え
- 春・夏・秋・冬で床・壁・植生のカラーパレットを変更
- **効果:** 四季のゲームテーマとビジュアルが連動

## 最終結論

**現在のCanvas 2D + コード生成のままでOTレベル（8/10以上）に到達することは不可能。**

これは技術スタックの問題ではなく、**「コードで描いた矩形」と「手描きのピクセルアート」の間にある本質的な品質差**の問題である。OTのHD-2Dは「優れたピクセルアートアセット」+「高品質なポストプロセス」の掛け算で成立しており、後者だけでは前者の不足を補えない。

ただし、悲観する必要はない。**現行のポストプロセス・エフェクト基盤は十分に強い。** ビネット・DOF・季節ティント・パーティクルといった「雰囲気を作るレイヤー」は既に4〜5割の完成度がある。**足りないのはアセットだけ。**

したがって、**Tier B（画像アセットの導入）が最もROIが高い選択**であり、既存のアーキテクチャを壊さずにビジュアル品質を2.5 → 6.5に引き上げることが可能。AI画像生成ツールを併用すれば、手描きスキルがなくてもHD-2D風タイルセットの制作は現実的である。
